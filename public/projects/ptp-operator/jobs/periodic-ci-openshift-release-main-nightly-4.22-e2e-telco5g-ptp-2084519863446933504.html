• Root Cause: The OCP 4.22.0-0.nightly-2026-07-22-152558 linuxptp-daemon image includes the intentional delayed-phc2sys-startup feature (introduced by k8snetworkplumbingwg/linuxptp-daemon#215): phc2sys is held in skipInitialStartup state and only launched by HandleDelayedPhc2sysStartup once ptp4l reports an offset below 1 second (daemon.go:2102). The release-4.22 test code at test/conformance/serial/ptp.go jumps directly to streaming phc2sys logs with a 1-minute timeout, so the context expires before phc2sys has emitted the selecting … as out-of-domain source clock line. For the parallel test, phc2sys not running means CLOCK_REALTIME never achieves the LOCKED state that parallel/ptp.go:393 waits for. The fix (bb43e35, "test: update CI tests for delayed phc2sys startup") explicitly inserts an Eventually gate waiting for the primary BC slave interface to reach SLAVE state before searching phc2sys logs, and is merged to main but not cherry-picked to release-4.22.

• Breaking PR/Commit:
• Linuxptp-daemon behavioral change: k8snetworkplumbingwg/linuxptp-daemon#215 (delayed phc2sys startup — synced into OCP 4.22 nightly)
• Missing test fix (main only): https://github.com/openshift/ptp-operator/commit/bb43e35bc01d23cfbb2aa9bee59b4cae193c2021 — NOT cherry-picked to release-4.22
• Related assertion fix (main only): https://github.com/openshift/ptp-operator/commit/402a5b07852f717809aad6e475323bc1907f0b2d — NOT cherry-picked to release-4.22

• Is it a flake? No — the release-4.22 test code has no mechanism to wait for phc2sys startup; every run against this image will deterministically time out until the fix is backported.

• Suggested Fix: Cherry-pick bb43e35 (and 402a5b0 for the related assertion fix) from main into release-4.22 of openshift/ptp-operator. Alternatively, consider backporting k8snetworkplumbingwg/linuxptp-daemon#215's context to release-4.22 documentation so the relationship between daemon behavior and test expectations is explicit.
