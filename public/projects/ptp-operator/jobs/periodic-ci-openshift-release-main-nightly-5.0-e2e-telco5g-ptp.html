TL;DR: A main-branch test regression (commit d20ffcbf) broke OS-clock-sync event parsing for 5 suites; T-BC and T-GM hardware-sync failures account for the remaining 9.



Root Cause Groups


• 5/14 failures — Event-value key schema mismatch (commit d20ffcbf) (suites: bc, dualfollower, dualnicbc, dualnicbcha\[parallel\], oc)

Commit d20ffcbf ("CNF-19588: CI test for clockClass recovery after cloud-event-proxy crash", merged 2026-07-03 on main) changed test/pkg/event/event.go:742–751 to key StoredEventValues by v.Resource (ResourceAddress, e.g. /cluster/node/.../CLOCK_REALTIME) instead of v.DataType ("notification", "metric"). For os-clock-sync-state-change events, all values share the same ResourceAddress, so only the last metric value survives in the map. The consumer in test/conformance/parallel/ptp.go:413–415 still reads values["notification"].(string) and values["metric"].(float64) — both always return zero-values — so wasLocked is never set to true and the 5-minute timeout fires unconditionally at ptp.go:393.

This is a deterministic regression, not a flake. The hardware IS achieving LOCKED state; the test simply cannot see it.


• 5/14 failures — T-BC FSM stuck in FREERUN (DPLL event pipeline failure) (suites: tbc)

The T-BC state machine in pkg/event/event_tbc.go requires inSyncConditionThreshold and toFreeRunThreshold to be initialized via DPLL-sourced events before it can transition out of PTP_FREERUN (see event_tbc.go:491–508, 593–597). On the tbc-profile nodes (e810 NICs with external PPS sync, ts2phcOpts: "-s generic -a --ts2phc.rh_external_pps 1"), DPLL event delivery appears broken in the release-5.0 production image, leaving the FSM permanently in FREERUN and causing all five serial tests that gate on PTP_LOCKED to time out. The convergeConfig function (event_tbc.go:657) that maps ptp4l interface events to the ts2phc/DPLL config namespace is the suspected fragility point for dual-NIC e810 topologies.


• 3/14 failures — T-GM GNSS lock not achieved; phc2sys blocked (suites: tgm)

The linuxptp-daemon intentionally delays phc2sys startup until HandleDelayedPhc2sysStartup (daemon.go:2094–2131) receives a ts2phc offset with |offset| < 1 000 000 000 ns. On GM node cnfdf32, ts2phc is running (its SIGTERM test passes) but never reports a sub-second offset, indicating GNSS synchronization was not achieved. Without GNSS lock, updateGMState (event.go:376) never reaches PTP_LOCKED, ptp4l never emits CLOCK_CLASS_CHANGE 6, the phc2sys metric stays at 0, and all three WPC GM assertions fail in turn. Hardware DPLL showing LOCKED (dpll=1) is not sufficient per event_test.go:92–95.


• 1/14 failures — DualNICBCHA phc2sys failover timeout (suites: dualnicbcha\[serial\])

The serial DualNICBCHA phc2sys failover test failed because phc2sys did not switch to the secondary interface within the 60-second test window after the primary was brought down. This may be a timing sensitivity or an infrastructure issue specific to the dualnicbcha topology.
