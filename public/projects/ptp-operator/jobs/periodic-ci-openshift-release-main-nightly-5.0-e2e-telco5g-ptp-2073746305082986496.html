TL;DR: All 32 failures trace to a single unlocked T-GM (ts2phc FREERUN) and a broken pmc command interface cascading across every suite.



Root Cause Groups:


• ~19/32 failures — T-GM ts2phc stuck in FREERUN (clockClass 248) while dpll=LOCKED (tgm: 10, dualnicbc: ~5, dualnicbcha: ~4): The GM node cnfdf32 never emits clockClass 6 because ts2phc_parser.go accumulates "source ts not valid" hits and forces ts2phcState = PTP_FREERUN, overriding a confirmed dpll LOCK. This starves every downstream suite — BC slave ports on the dualnic nodes have no locked upstream grandmaster to sync to, so they remain MASTER/FREERUN themselves, cascading into all WPC GM state, holdover, recovery, and event-timeout failures across all three suites.

• ~13/32 failures — pmc rejects GET PARENT_DATA_SET as two "bad command" tokens (dualnicbc: 5, dualnicbcha: 4, cross-suite overlap ~4): Tests calling ptptesthelper.go:106 via pmc interactive mode receive bad command: GET / bad command: PARENT_DATA_SET for every query, blocking all clock-identity discovery. The two-token error pattern is diagnostic of either (a) the unpinned linuxptp RPM in Dockerfile.ocp updating to ≥4.2 where management_enabled=0 is the new default, or (b) a code path in pmc.go passing "GET PARENT_DATA_SET" as a single unsplit argument to exec.Command. This blocks "Slave can sync to master", "Downstream slave can sync to BC master", and "higher priority" tests in both dualnic suites.

Suite TL;DR: The dualnicbcha suite experienced two cascading failure streams: pmc command-format rejection (bad command: GET / bad command: PARENT_DATA_SET) blocking clock-ID discovery, and the BC slave interface (ens2f0np0) stuck in MASTER instead of SLAVE state, leaving the full BC sync chain in FREERUN with all downstream event/metric tests timing out.



Root Cause Groups:


• Group 1: pmc rejects GET PARENT_DATA_SET — clock identity discovery blocked (affects: "Slave can sync to master", "Downstream slave can sync to BC master")
• Evidence:


Identical error pattern in the dualnicbc suite confirms this is systemic, not suite-specific.

• Root Cause: The test framework (from ptp-operator/main) calls pmc inside the linuxptp-daemon pod with GET PARENT_DATA_SET format. The pmc binary in the release-5.0 linuxptp-daemon image is installed as the linuxptp RPM from the RHEL9 base image (registry.ci.openshift.org/ocp/5.0:base-rhel9). No RPM version is pinned in Dockerfile.ocp (yum install linuxptp, line 11). If the linuxptp RPM was recently updated to a version where the interactive-mode command parser no longer treats GET as a valid action keyword — processing each whitespace-separated token as a standalone command — both GET and PARENT_DATA_SET produce bad command errors. The two-error pattern (one per token) is diagnostic: a connection failure would produce no output; a single-token error would produce one bad command; two sequential bad command responses confirm each word is parsed independently. Additionally, linuxptp-daemon/pkg/pmc/pmc.go:294 on main contains a related bug where RunPMCGetParentDS passes "GET PARENT_DATA_SET" as a single compound argument to exec.Command rather than splitting it into "GET", "PARENT_DATA_SET" — this would cause identical symptoms in non-interactive mode if that code path is reached.
• Breaking PR/Commit: Unknown — the relevant change is in the RHEL9 linuxptp RPM (unpinned in Dockerfile.ocp) or in ptp-operator main test code at ptptesthelper.go:106. The linuxptp-daemon upstream-sync PR #617 (fd6ff1e, merged 2026-06-30) is on main only; its effect on release-5.0 images is unverified without check_backport.py.
• Is it a flake? No — identical error across two suites (dualnicbc and dualnicbcha) in the same run, same pmc binary, deterministic command-format mismatch.
• Suggested Fix: Pin the linuxptp RPM to a known-working version in Dockerfile.ocp, or update the test helper at ptptesthelper.go:106 to use GET + PARENT_DATA_SET as separate exec.Command arguments (or quote/send them as a single string to pmc's interactive stdin). Cross-check with the linuxptp upstream changelog for pmc command-syntax changes.
