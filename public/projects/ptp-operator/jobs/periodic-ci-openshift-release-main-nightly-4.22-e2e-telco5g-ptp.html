TL;DR: 14 failures across 7 suites caused by three deterministic main-branch test regressions and one production daemon defect.



Root Cause Groups


• 5/14 failures — event.go StoredEventValues key collision (PR #711 / commit d20ffcb) (suites: bc, dualfollower, dualnicbc, dualnicbcha, oc)

Commit d20ffcbf0cec (merged main ~2026-07-08) changed createStoredEvent in test/pkg/event/event.go to key StoredEventValues by v.Resource (full resource path, e.g. /cluster/node/.../CLOCK_REALTIME) instead of v.DataType ("notification" / "metric"). Because both the notification (LOCKED) and metric (-17) entries for OsClockSyncStateChange share the same resource address, the second loop iteration overwrites the first, leaving values["notification"] as nil. The parallel test testSyncState() in test/conformance/parallel/ptp.go:391 does values["notification"].(string), gets "", and after the full 5-minute soak window fails with "OS Clock was never LOCKED". The underlying clocks were genuinely LOCKED throughout (serial event tests pass); this is a pure test-code defect on main not cherry-picked to release-4.22.


• 5/14 failures — T-BC test code incompatible with release-4.22 images (PR #205 / commit 84723c83) (suites: tbc)

New T-BC test code merged to main in PR #205 (aede1e93, 84723c83) was never validated against release-4.22 production images. At least three distinct incompatibilities are present: (1) GetFullDiscoveredConfig returns nil for DiscoveredSlave1PtpConfig in the TBC environment, causing a nil-dereference in BasicClockSyncCheck at ptp.go:905; (2) the daemon log regex Profile Name: _tbc-t(r|t) does not match any output within TimeoutIn3Minutes, indicating a log format mismatch; and (3) GetClockIDMaster invokes PMC against the default socket /var/run/ptp4l.0.config instead of the T-BC dual-instance sockets (_tbc-tr.config / _tbc-tt.config), yielding bad command: GET / bad command: PARENT_DATA_SET. A suite-level timeout is the downstream cascade.


• 3/14 failures — T-GM drops to FREERUN immediately on GNSS loss instead of entering holdover (suites: tgm)

In the release-4.22 linuxptp-daemon production image, event.go:412 forces ts2phcState = PTP_FREERUN as soon as NoSourceTSCount >= 2 (two consecutive "source ts not valid" log lines from ts2phc). Because ts2phc emits this message in rapid succession on GNSS loss, NoSourceTSCount hits 2 almost instantly, collapsing clock class to 248 (FREERUN) before any holdover window (class 7) can be established. Test 3 confirms a transient class-7 transition exists but is overridden before the next 2-second metric poll; test 2 is a cascade failure because test 1 left the T-GM stuck at class 248.


• 1/14 failures — phc2sys HA failover switch log never observed within 60-second window (suites: dualnicbcha)

After primary interface ens2f1 was taken down at 10:41:33, GetPodLogsRegexSince in pods.go:162 streamed linuxptp-daemon-container logs for exactly TimeoutIn1Minute watching for the phc2sys source-clock-switch regex, but the context deadline fired at 10:42:38 with no match. This may reflect phc2sys requiring multiple announce-timeout cycles before declaring source loss, or a regression in linuxptp-daemon PR #629 (14eb788, merged 2026-07-22 on release-4.22) which refactored phc2sys log parsing.

Suite: dualfollower (1 failures)


Suite TL;DR: The single parallel "Event based tests PTP Slave Clock Sync" failure is a test regression introduced on July 3, 2026 in main: event.go was changed to key StoredEventValues by resource address instead of data_type, causing the OsClockSyncStateChange event's "LOCKED" state to be silently overwritten and never parsed, so wasLocked is never set and the test times out.


Root Cause Groups:


• Group 1: StoredEventValues key collision — event state parsing broken (affects: [It] [dualfollower-parallel] Event based tests PTP Slave Clock Sync)
• Evidence:

• Root Cause: Commit d20ffcb ("CNF-19588: CI test for clockClass recovery after cloud-event-proxy crash", test/pkg/event/event.go) changed StoredEventValues keying from v.DataType to v.Resource (ResourceAddress) to avoid collisions in BC-mode clock class events. However, for OsClockSyncStateChange events, both the "notification" value ("LOCKED") and the "metric" value (-17) share the same ResourceAddress (/cluster/node/.../CLOCK_REALTIME). In the loop at event.go:743–752, the metric entry (second iteration) overwrites the notification entry (first iteration), leaving values = {"/cluster/node/.../CLOCK_REALTIME": "-17"}. The parallel test's testSyncState() at parallel/ptp.go:391 then reads values["notification"].(string) which returns "" (nil type assertion), so state = "", wasLocked is never set to true, and after the full 5-minute Duration:5 soak timer the test fails with "OS Clock was never LOCKED". The d20ffcb commit updated event.go and added a new serial test in serial/ptp.go, but missed updating testSyncState in parallel/ptp.go. The clock itself was genuinely LOCKED the entire time (serial tests pass; metrics confirm LOCKED state on node cnfdf32). The same failure hits bc, dualnicbc, dualnicbcha, oc parallel suites for the identical reason.
• Breaking PR/Commit: d20ffcb — "CNF-19588: CI test for clockClass recovery after cloud-event-proxy crash" — https://github.com/openshift/ptp-operator/commit/d20ffcb (merged July 3, 2026, main only; not cherry-picked to release-4.22)
• Is it a flake? No — deterministic regression. The clock was stable-LOCKED, so the stale initial state notification was the only event received; the parsing failure makes state = "" on every run.
• Suggested Fix: In test/conformance/parallel/ptp.go testSyncState(), replace the values["notification"].(string) and values["metric"].(float64) lookups with resource-address-based lookups (e.g., iterate over values to find a string value matching a known sync state, or look up the full resource path "/cluster/node//CLOCK_REALTIME"). Alternatively, fix event.go to store StoredEventValues with BOTH the data_type key and the resource address key so backward-compatible code continues to work.
