Cross-Suite Summary — periodic-ci-openshift-release-main-nightly-5.0-e2e-telco5g-ptp-upstream


Version: 5.0 | Total failures: 36 | Suites: bc, dualfollower, dualnicbc, dualnicbcha, tbc, all, tgm


TL;DR: Three independent main-branch regressions — a test key-scheme bug, a broken PMC invocation, and a T-BC topology mismatch — plus a ts2phc servo regression in the upstream sync caused all 36 failures.



Root Cause Groups


• 2/36 failures — createStoredEvent() key-scheme change drops LOCKED state (suites: bc, dualfollower)

Commit d20ffcbf (PR #171, "CNF-19588") changed test/pkg/event/event.go's createStoredEvent() to key the StoredEventValues map by v.Resource (ResourceAddress) instead of v.DataType. For OsClockSyncState events both the notification ("LOCKED") and metric ("-18") share the identical ResourceAddress, so the metric silently overwrites the notification in the loop. The test then reads values["notification"] and finds nothing, wasLocked is never set, and the test times out — even though the production cloud-event-proxy correctly delivered LOCKED.


• 21/36 failures — PMC command split + BC/HA clock stuck at FREERUN (clock class 248) (suites: dualnicbc, dualnicbcha)

Commit 14eb788 (PR #629, "Sync from upstream 22-Jul-2026" in k8snetworkplumbingwg/linuxptp-daemon) introduced a behavioral regression where pmc receives GET and PARENT_DATA_SET as two separate argv tokens instead of a single quoted string, returning bad command: GET / bad command: PARENT_DATA_SET for every PMC call. This prevents the test from reading parentPortIdentity or grandmasterIdentity, causing role-assertion failures (ens2f0np0 stays in MASTER instead of SLAVE) and preventing clock class from ever reaching 6. All downstream clock-sync, outage-recovery, event-API, and metrics tests cascade from this single invocation bug.


• 2/36 failures — T-BC topology solver returns zero solutions (suites: tbc, all)

Commit 84723c83 (PR #205, "test: Add T-BC CI tests and configuration") added PtpConfigTelcoBC() and its AlgoTelcoBCString="TBC" constraint set to test/pkg/testconfig/testconfig.go, requiring a WPC NIC with receiver + two same-NIC transmitter ports and a co-located WPC GM. The CI cluster (cnfdf30–cnfdf32) does not have this physical topology — only cnfdf32 has WPC hardware (confirmed as the TGM node). SynchronizedBeforeSuite calls CreatePtpConfigurationsWithRetry(3), the solver returns empty, and the suite is torn down before any test runs.


• 11/36 failures — WPC T-GM ts2phc servo stuck in FREERUN despite DPLL LOCKED (suite: tgm)

Also attributable to commit 14eb788 (PR #629 upstream sync). DPLL hardware on cnfdf32 reports LOCKED (dpll=1) confirming valid GNSS/1PPS, but ts2phc software servo stays at FREERUN (ts2phc=0), indicating a regression in ts2phc log parsing, servo state-machine advancement, or GM clock-class propagation introduced by the sync (log_parsing.go:82–153, ProcessTs2PhcEvents in daemon.go:2134–2190). With ts2phc in FREERUN, HandleDelayedPhc2sysStartup never fires, phc2sys stays down (process_status=0), ptp4l clock class stays at 248, no CloudEvent LOCKED events are emitted, and all log-stream tests hit context deadline.

Root Cause Groups:


• Group 1: Test code key-scheme change in createStoredEvent() silently hides LOCKED state (affects: [It] [bc-parallel] Event based tests PTP Slave Clock Sync)
• Evidence:

The raw cloud event data (logged by event.go: 730) clearly shows:

```json

{"values":[

{"ResourceAddress":"...CLOCK_REALTIME","data_type":"notification","value_type":"enumeration","value":"LOCKED"},

{"ResourceAddress":"...CLOCK_REALTIME","data_type":"metric","value_type":"decimal64.3","value":"-18"}

```

The LOCKED event was delivered, but values["notification"] and values["metric"] were both nil in the test.


• Root Cause: Commit d20ffcbf (PR #171, CNF-19588) changed createStoredEvent() in test/pkg/event/event.go (v1 path lines 711–717, v2 path lines 742–751) from using v.DataType as the map key to using v.Resource (the ResourceAddress). For OsClockSyncState events the notification value and metric value share the same ResourceAddress (/cluster/node/.../CLOCK_REALTIME), so the metric entry (-18) overwrites the notification entry (LOCKED) in the loop. The test at ptp.go:414-415 then reads values["notification"] and values["metric"] — both return nil because those keys no longer exist — so state is "" instead of "LOCKED", wasLocked is never set true, and the test times out at ptp.go:393.

• Breaking PR/Commit: Commit d20ffcbf0cecd1cf94987788c703fa8d4565ba4d — "CNF-19588: CI test for clockClass recovery after cloud-event-proxy crash" (merged as [PR #171](https://github.com/k8snetworkplumbingwg/ptp-operator/pull/171) on main). This is a main-only test code change; the release-5.0 production images are unaffected. The OS clock on the hardware IS reaching LOCKED — the cloud event confirms it — but the test framework can't see it.

• Is it a flake? No — the bug is deterministic. Every run will fail to observe LOCKED until the test times out.

• Suggested Fix: In test/pkg/event/event.go's createStoredEvent(), use a composite key : (or fall back to DataType when ResourceAddress is empty), so that OsClockSyncState events retain distinct "notification" and "metric" entries while BC clock class events with multiple "metric" values on different resources still don't collide. Alternatively, update ptp.go:414-415 to iterate the values map and match by DataType rather than by fixed string keys.
