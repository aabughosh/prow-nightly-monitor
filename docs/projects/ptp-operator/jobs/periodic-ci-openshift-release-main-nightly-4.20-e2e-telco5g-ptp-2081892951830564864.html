Version: 4.20 | Total failures: 26 | Suites: bc, dualfollower, dualnicbc, dualnicbcha, tbc, tgm


TL;DR: PTP hardware never synced cluster-wide, a new TBC test deployed an unsupported config, and the TGM holdover state machine skipped ClockClass 7.



Root Cause Groups


• 19/26 failures — Environment-wide PTP synchronization failure (suites: bc, dualfollower, dualnicbc, dualnicbcha, tbc-partial)

Every test helper that reads linuxptp-daemon-container log streams (GetForeignClockID, GetProfileName in ptp-operator/test/pkg/ptphelper/ptphelper.go) timed out with either context deadline exceeded or timedout waiting for matches, because ptp4l never reached servo state s2 (LOCKED) on any node. The failure is simultaneous across at least 9 distinct daemon pod names on all worker nodes, ruling out a single-node or single-profile fault and pointing to the PTP grandmaster timing reference (GNSS signal or lab hardware path) being unavailable or degraded for the entire ~3h45m run. No daemon image pull failures were observed; the operator deployed successfully at version 4.20.0.


• 7/26 failures — New TBC dual-profile PtpConfig not reconciled by production daemon (suites: tbc)

The TBC suite was introduced in main by commit aede1e9 ("T-BC tests", 2026-06-23) via createTelcoBCConfig (testconfig.go:1967), which creates a novel dual-profile PtpConfig CR (test-wpc-tbc) using controllingProfile in PtpSettings to link receiver profile tbc-tr and transmitter profile tbc-tt. The production release-4.20 linuxptp-daemon binary predates this dual-profile controller logic; applyNodePtpProfile never processes the CR, so printNodeProfile (daemon.go:971,1521) never writes the Ptp4lConf: #profile: test-wpc-tbc line that every TBC test depends on via GetProfileLogID (ptphelper.go:84). All seven test retries (3-minute deadline, 1-minute stream windows) exhaust and return the two observed timeout variants.


• 3/26 failures — TGM holdover state machine skips ClockClass 7; FREERUN event not published on ts2phc exit (suites: tgm)

On node cnfdf32, when GNSS is disabled, ts2phc transitions directly from LOCKED (ClockClass 6) to FREERUN (ClockClass 248) without passing through PTP_HOLDOVER; the ClockClass 7 gate in pkg/event/event.go:460,499,509 is therefore never triggered. Concurrently, when ts2phc terminates, the ptp-clock-class-change metric is updated to 248 but the ptp-state-change FREERUN event is never published — the subs.LOCKSTATE channel receives no notification while subs.CLOCKCLASS does — indicating a gap in daemon.go's ts2phc-exit path versus a graceful state-machine transition. The most recent release-4.20 linuxptp-daemon merge touching this path is OCPBUGS-88741 (openshift/linuxptp-daemon#612, merged 2026-06-16, commit c522d1efe6).

Actionable Recommendations


1. Investigate the lab PTP grandmaster immediately. The simultaneous failure of all 5 non-TGM suites across 9+ daemon pods is the highest-signal indicator of a GM-level outage (GNSS feed, fiber/PPS cable, or upstream T-GM holdover expiry). Pull ts2phc and ptp4l logs directly from every linuxptp-daemon-* pod (oc logs -n openshift-ptp -c linuxptp-daemon-container) and check for offset lines — if none appear, the GM is not sending. Retry the full job only after the GM is confirmed healthy; a retry on a broken environment will waste CI resources.

2. Gate the new TBC test suite on daemon version. The tbc suite's createTelcoBCConfig deploys a dual-profile controllingProfile CR that the release-4.20 (and release-4.22) production daemon cannot reconcile. Either backport the dual-profile controller logic to release-4.20 (track the upstream main commit aede1e9), or add a SkipIfDaemonVersionBelow guard in testconfig.go so the suite is skipped until the supporting daemon is available. Without this fix the 7 TBC failures are guaranteed to recur on every release-4.20 nightly regardless of lab health.

3. File a targeted bug for the TGM holdover / FREERUN event gap and bisect OCPBUGS-88741. The cnfdf32 TGM state machine skipping ClockClass 7 and the missing ptp-state-change FREERUN event on ts2phc exit are reproducible, code-level regressions independent of lab health. Audit pkg/event/event.go (lines 460, 499, 509) and the ts2phc process-exit handler in daemon.go against pre-OCPBUGS-88741 behavior. If bisection confirms c522d1efe6 as the culprit, revert or patch only that path, and add a unit test asserting ClockClass 6 → 7 → 248 ordering after GNSS disable.

• Evidence:

• Test 3 (GNSS reboot and recovery), failure message:

> [FAILED] expected a metric [7.000000] but got map[/cluster/node/cnfdf32.telco5gran.eng.rdu2.redhat.com/ens7fx/master:248] — ptp.go:4157 @ 07/28/26 08:49:47

• After GNSS reboot the metric API shows ClockClass 248 (FREERUN) instead of 7 (LOCKED).

• Root Cause: Three independent symptoms share one upstream cause: the WPC T-GM on cnfdf32 does not transit through ClockClass 7 (holdover in-spec) when GNSS is disrupted. The state machine in pkg/event/event.go sets ClockClass 7 only when ts2phc reports a PTP_HOLDOVER state (lines 460, 499, 509 of event.go); instead ts2phc is jumping directly from LOCKED to FREERUN without entering HOLDOVER, resulting in the clock class skipping straight to 248. Concurrently, the ptp-state-change (synchronization state) event is not published with FREERUN when ts2phc terminates — only the ptp-clock-class-change metric is updated to 248 — indicating a gap in the event publishing path when the daemon detects ts2phc exit vs. a graceful state-machine transition. Test 3 then runs on a GM already stuck in FREERUN from tests 1 and 2's unrecovered GNSS disruptions.

• Breaking PR/Commit: The most recent release-4.22 linuxptp-daemon merge is OCPBUGS-88741 (openshift/linuxptp-daemon#612, merged 2026-06-16, commit c522d1efe6), which changed e825 DPLL pin initialization for T-GM: "T-GM will disable e825 outputs to DPLL on init." Disabling these DPLL outputs on init could prevent the DPLL from entering a proper holdover state (ClockClass 7) when GNSS is lost, causing it to skip directly to FREERUN. A second candidate is OCPBUGS-94177 (openshift/linuxptp-daemon#618, merged 2026-06-30, commit cf3c0f313f), which delays phc2sys startup until ts2phc offset is <1.0s; if this delay logic interacts with the GNSS coldboot path it could suppress or race past the holdover transition. Neither commit SHA was found on main's local clone (backport check: NOT_PRESENT for 14eb788); the test scripts come from main while the production images come from release-4.22. Hardware flakiness on the GNSS receiver of cnfdf32 cannot be ruled out without checking peer runs.

• Is it a flake? Possibly — the cascade failure pattern (test 1 disrupts GNSS, tests 2 and 3 inherit the degraded GM) could amplify an underlying marginal hardware or timing condition on cnfdf32. However, the missing ptp-state-change/FREERUN event in test 2 is a reproducible structural issue in the daemon's event path.

• Suggested Fix: Run the job again to determine if the holdover-skip is consistent or intermittent; if consistent, bisect between c522d1efe6 (OCPBUGS-88741, DPLL pin config) and the current release-4.22 HEAD by checking whether the DPLL on cnfdf32 enters holdover state (dpll_state == HOLDOVER) after GNSS loss. If the DPLL never enters holdover, the DPLL pin disable in #612 is the suspect; if it does enter holdover but ts2phc doesn't report it, the ts2phc log-parser or the ptp-state-change event publisher in pkg/event/event.go needs investigation.
