Cross-Suite Patterns


• Hardware sync failure is the dominant cross-suite thread. Root causes 1 and 2 both point to the RDU2 test nodes (cnfdf30–32) failing to maintain a healthy PTP grandmaster-to-slave chain during this job window. tgm (ts2phc FREERUN on the GM node) and dualnicbc/dualnicbcha (clockClass/port-state failures on BC nodes) are facets of the same degraded physical sync fabric.

• The PMC split-args bug (root cause 3) is strictly test-code and suite-independent. It affects every suite that exercises the getClockIDViaPMC fallback path — currently triggered only in dualnicbc and dualnicbcha because their log format misses the primary log-parsing path. bc-serial escapes because it locates the clock ID via log parsing before reaching the broken fallback.

• The parallel soak timeout (root cause 4) is cross-suite by construction. All five parallel sub-suites (bc-parallel, dualfollower-parallel, dualnicbc-parallel, dualnicbcha-parallel, oc-parallel) run the same testSyncState test against the same cluster-event infrastructure. Their simultaneous failure at ≈363 seconds is a single shared event, not five independent regressions.

• Suite-specific failures: tbc's BeforeAll topology failure is isolated to that suite; tgm's ts2phc FREERUN affects only the GM node tests.


This matches the existing pattern in ptptesthelper.go:588 (GetClockClassViaPMC) and will immediately unblock ~5 deterministically failing tests in dualnicbc and dualnicbcha.


2. Investigate and remediate the RDU2 hardware sync chain (cnfdf30–32).

Both the ts2phc FREERUN (tgm) and the BC slave MASTER-state / clockClass-248 failures (dualnicbc, dualnicbcha) trace to the physical PTP grandmaster-to-slave path being degraded during this run window. Check GNSS/GPS signal quality on the GM node, verify the T-GM NIC (ens7fx/WPC card) cable and SFP state, and confirm DPLL lock propagation from GM to BC nodes before re-running.

Suite: dualnicbc (11 failures)


Suite TL;DR: A split-args bug in the newly introduced getClockIDViaPMC helper causes PMC commands to be rejected by the pmc binary, timing out all ClockSync tests; cascading config disruption and an event-consumer timeout account for the remaining failures.



Root Cause Groups:


• Group 1: PMC split-args bug in getClockIDViaPMC (affects: Slave can sync to master, Downstream slave can sync to BC master, Can provide a profile with higher priority)

• Evidence:

```

parentPortIdentity.clockIdentity not found in pmc output for /var/run/ptp4l.1.config: bad command: GET

bad command: PARENT_DATA_SET

grandmasterIdentity not found in pmc output for /var/run/ptp4l.1.config: bad command: GET

bad command: PARENT_DATA_SET

Timed out after 203.731s. / 203.074s. / 201.562s.

```


• Root Cause: getClockIDViaPMC in test/pkg/ptphelper/ptphelper.go (introduced in commit d20ffcbf0c, merged via 855c9e1493 2026-07-07) passes the pmc batch command as two separate slice elements — "GET" and "PARENT_DATA_SET" — rather than the single combined string "GET PARENT_DATA_SET":

```go

// BUGGY (ptphelper.go:144):

[]string{"pmc", "-b", "0", "-u", "-f", configFile, "GET", "PARENT_DATA_SET"}

// CORRECT (ptptesthelper.go:588, same repo):

[]string{"pmc", "-b", "0", "-u", "-f", configFile, "GET PARENT_DATA_SET"}

```

The linuxptp pmc binary processes each remaining argv element as a complete batch command. Receiving "GET" alone produces bad command: GET; "PARENT_DATA_SET" alone produces bad command: PARENT_DATA_SET. The getClockIDViaPMC fallback (reached when log-regex parsing misses the dualnicbc log format) therefore always fails, and the Eventually wrapper (3-minute timeout) exhausts before returning, failing these tests. bc-serial passes the equivalent tests because it finds the clock ID via log parsing and never reaches the broken pmc fallback.


• Breaking PR/Commit: d20ffcbf0c / merged 855c9e1493 — _"CNF-19588: CI test for clockClass recovery after cloud-event-proxy crash"_ — test/pkg/ptphelper/ptphelper.go — [https://github.com/openshift/ptp-operator/commit/855c9e1493](https://github.com/openshift/ptp-operator/commit/855c9e1493)

• Is it a flake? No — the split-args bug produces bad command on every invocation, deterministically.

• Suggested Fix: Merge the two separate args into one in ptphelper.go: change "GET", "PARENT_DATA_SET" to "GET PARENT_DATA_SET" as a single slice element, consistent with how GetClockClassViaPMC in ptptesthelper.go:588 already invokes pmc.


• Group 2: ptp4l clock class stuck at FREERUN (248) (affects: Verify clockClass when locking PTP source on dual NIC boundary clock, Should recover clockClass via event API after cloud-event-proxy crash, BC clock class recovers to Locked after upstream link outage)

• Root Cause: By the time these tests run (>670 s into the suite), test 3 ("Can provide a profile with higher priority") has timed out at 261 s while the temporary high-priority PtpConfig "temp" was still active. Although DeferCleanup(RestorePtp4lConf) fires, the ensuing ptp4l restart on the dualnicbc node means the second ptp4l instance (ptp4l.1) must re-acquire lock. The clockClass tests' 5-minute Eventually windows overlap with this re-sync period. Additionally, EnableGMCapableInPlace (used in test 4 at ptp.go:1256) explicitly injects clockClass 248 into the PtpConfig to create test conditions; if RestorePtp4lConf does not take effect fast enough before subsequent polling, all three clockClass assertions see 248. The correct GetClockClassViaPMC call format ("GET PARENT_DATA_SET" as a single arg at ptptesthelper.go:588) rules out the same pmc bug.

• Breaking PR/Commit: Same 855c9e1493 (test-ordering/cleanup-timing consequence of the Group 1 regression); no independent code regression confirmed for this group.

• Is it a flake? Partially — the cascade is deterministic given Group 1's timeouts, but the exact re-sync window makes this timing-sensitive.

• Suggested Fix: Fix Group 1 first; additionally add a post-DeferCleanup wait for ptp4l re-lock before handing off to the next test, and ensure EnableGMCapableInPlace is always accompanied by a synchronous restore check.


• Group 3: Interface role and process-state cascade (affects: The slave node network interface is taken down and up, Should restart phc2sys with no socket errors after SIGTERM, PTP metric is present verifies on slave)

• Evidence:

• Root Cause: With ptp4l.1 in FREERUN (clock class 248, no upstream lock — see Group 2), the port that should be SLAVE (ens2f0np0) remains in MASTER role because ptp4l acts as a grandmaster candidate. phc2sys does not start when ptp4l is unlocked (process status=0). PTP time-sync metrics (openshift_ptp_*) are not emitted without a locked clock state. All three symptoms are downstream of the same unlocked ptp4l.1 state, compounded by the config disruption from Group 1/2.

• Breaking PR/Commit: Same cascade from 855c9e1493. No independent breaking commit identified.

• Is it a flake? No — deterministic cascade.

• Suggested Fix: Resolving Group 1 and ensuring clean state restore between tests (Group 2) should clear these failures.


• Group 4: Event consumer pod log deadline (affects: Should receive events after linuxptp-daemon pod restart, [dualnicbc-parallel] Event based tests PTP Slave Clock Sync)

• Root Cause: Both the serial and parallel event tests fail because the consumer pod in namespace ptp-event-framework-test does not emit logs within the deadline. This consumer pod is established by the event test setup and depends on the cloud-event-proxy sidecar publishing a SyncStateChange event; with ptp4l in FREERUN (Group 2), no valid sync-state transition is ever published, so the consumer pod log stream never produces the expected line and the context deadline fires. The parallel test independently hits the same consumer pod and likewise times out.

• Breaking PR/Commit: Cascade from Group 2; event framework code unchanged. Unknown if there is a separate event-consumer pod startup bug.
